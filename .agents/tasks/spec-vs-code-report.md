## Detailed Evidence

### a) Subnets públicas

**O que a spec diz**

`requirements.md` R2.2 lista explicitamente os seguintes `aws_subnet`:
```
- aws_subnet pública:    10.0.1.0/24, us-east-1a
- aws_subnet privada-a:  10.0.2.0/24, us-east-1a
- aws_subnet privada-b:  10.0.3.0/24, us-east-1b
```
Ou seja, a spec atual descreve **uma única subnet pública** em `us-east-1a`.

`design.md` repete o mesmo layout:
```
Subnet pública 10.0.1.0/24 ◄── IGW ◄── Internet
Subnet privada-a 10.0.2.0
Subnet privada-b 10.0.3.0
```

**O que o código faz**

`terraform/modules/networking/main.tf` cria exatamente o que a spec descreve:
```hcl
resource "aws_subnet" "public_a" {
  cidr_block              = "10.0.1.0/24"
  availability_zone       = "us-east-1a"
  map_public_ip_on_launch = true
  ...
}
```
O output `public_subnet_id` retorna apenas `aws_subnet.public_a.id` (singular).

**Divergência**

Código e spec atuais estão alinhados em 1 subnet pública. A divergência é entre o **pedido do usuário** ("ter duas subnets públicas em zonas diferentes") e a spec+código atuais. A spec precisa ser atualizada para incluir uma segunda subnet pública (ex: `10.0.4.0/24`, `us-east-1b`), e o código seguirá depois.

### c) Security Group EC2 — SSH porta 22

**O que a spec diz**

`requirements.md` R2.2:
> `aws_security_group` ec2: ingress 80 de 0.0.0.0/0, ingress 22 de **var.ssh_allowed_cidr**, egress livre

`requirements.md` R2.7:
> `ssh_allowed_cidr`: default "0.0.0.0/0" com aviso na description

`design.md` (Segurança):
> SSH aberto | ssh_allowed_cidr com aviso; **restringir ao IP do aluno em produção**

**O que o código faz**

`terraform/modules/networking/main.tf`:
```hcl
ingress {
  description = "SSH restrito ao CIDR configurado (menor privilegio)"
  from_port   = 22
  to_port     = 22
  protocol    = "tcp"
  cidr_blocks = [var.ssh_allowed_cidr]
}
```
`terraform/modules/networking/variables.tf`:
```hcl
variable "ssh_allowed_cidr" {
  default = "0.0.0.0/0"
  description = "... TODO: Restrinja ao seu IP público (ex: 203.0.113.10/32) em produção."
}
```

**Divergência**

Tecnicamente, código e spec estão alinhados: SSH é liberado para `var.ssh_allowed_cidr`, cujo default é `0.0.0.0/0`.  
O que está ausente na spec é uma **exigência** de que o aluno substitua o default pelo seu IP. O usuário quer que a spec diga explicitamente que o valor deve ser o IP do aluno (ex: `203.0.113.X/32`), não apenas um aviso opcional.

## Conclusions and Recommendations

As cinco mudanças pedidas pelo usuário estão **ausentes ou incompletas na spec**. Nenhuma delas é um bug no código atual — o código implementa exatamente o que a spec descreve. As atualizações necessárias são:

### 1. Segunda subnet pública em zona diferente
**Arquivo:** `requirements.md` → R2.2  
**Mudança:** Adicionar `aws_subnet` pública-b: `10.0.4.0/24`, `us-east-1b`, `map_public_ip_on_launch = true`.  
**Impacto no design:** `design.md` precisa refletir 2 subnets públicas no diagrama. O output `public_subnet_id` do módulo networking vira uma lista (ou dois outputs separados: `public_subnet_ids`), e o módulo compute precisa aceitar qual usar.

### 2. Tipo de instância EC2
**Nenhuma mudança necessária.** Spec e código já concordam em `t3.medium`. Confirmar com o professor se a prova exige outro tipo.

### 3. SSH restrito ao IP do aluno
**Arquivo:** `requirements.md` → R2.2 e R2.7  
**Mudança:** Remover o default `0.0.0.0/0` da variável `ssh_allowed_cidr` (ou torná-la obrigatória sem default) e exigir que o aluno preencha com seu IP (`/32`) no `terraform.tfvars`. Adicionar validação `can(regex("^\\d+\\.\\d+\\.\\d+\\.\\d+/32$", var.ssh_allowed_cidr))`.

### 4. Output `public_ip`
**Arquivo:** `requirements.md` → R2.1 e R2.4; `design.md` → módulo compute  
**Mudança:** Adicionar `public_ip` como output do módulo compute (`aws_instance.moodle.public_ip`) e do root `outputs.tf`. Atualizar a spec nos dois locais.

### 5. `terraform-plan` em PRs com comentário
**Arquivo:** `requirements.md` → R5.1; `design.md` → CI/CD  
**Mudança:** Adicionar trigger `pull_request` ao `terraform-plan.yml`. Adicionar step que captura o output do `terraform plan` e posta como comentário no PR (padrão: `actions/github-script` + `github.rest.issues.createComment`). Atualizar a spec para descrever o novo trigger e o step de comentário.
